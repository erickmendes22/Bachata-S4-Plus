# n054 — restore decoupled FSR activation after n052

## Confirmed regression

Device report C223140D (Bloodborne CUSA03173 01.09, FEX/core025) has a validated 640x360 camera scene and a separate 1920x1080 HUD image. n052 rejected that layout with REJECTED_UNRELATED_LDR and recorded no real AMD dispatch. Its test fixture allowed precisely this production-rejected layout through BS4_TEST_ALLOW_DECOUPLED_SCENE.

## Change

Remove the same-backing requirement and the fixture-only permission. Retain camera/depth, stored full-scene rectangle, rewrite invalidation, native MovieShader boundary and successful single-queue submission checks. Continue preferring a newer validated local final-color pass over the submitted reduced-size candidate. A different HUD image alone no longer invalidates the scene. Preserve existing n052 bounded readbacks and log budgets; two decoupled-route records total are added. Neither arbitrary RGB changes nor speculative render-pass interruption are introduced.

The diagnostic records final_color_identity_proven=0 for decoupled candidates: valid dimensions/order do not establish that a texture is the final tone-mapped scene. This correction restores activation; it is not proof of eliminating the phone cyan flash.

## Validation

GitHub run 38721631412, SDK source 604a8ba9a9abd3d26557f8fb53e1a8c0f10587ba:
- ARM64 glibc SDK built.
- Decoupled cross-CB scene: seven real AMD temporal frames, 640x360 -> 1280x720, original HUD preserved, zero Vulkan validation errors.
- Negative control reinstating the n052 same-backing restriction fails the image assertion and records no real dispatch.
- Same-target final LDR selection and its old-selection negative control still pass.
- Prior tests cover depth clears, partial/unstored passes, local and cross-CB overwrites, camera history, FP16 dependencies, abandoned recording, retained resources after dispatch failure, and bounded WSI probes.
- No production host-only allow/negative-control strings in the ARM64 SDK.

## Packaging and limits

Use the retained n040 package, SHA256 6cecb04c4dbb5f316d820e97d2cdc1bbf86731dde5b379773908ced68f7ff6b9, as the unchanged Android/runtime container. The available n043–n046 and n050–n052 packaging scripts describe SDK-only updates; the native core025 SHA matches n052 exactly (c1cf8986c2a5f6f9f33d32a073eff797e2717b4848cd475c4d19f26dc7042bb2). Replace only libbachata_fsr31.so and runtime identity/checksum metadata. Validate every runtime entry and every untouched APK entry. No core compilation or core023.

Physical-device activation, the intermittent cyan flash and guest heap panic are not established as corrected by these software Vulkan results. n054 is an activation-regression correction, not a claim of full visual/stability parity with the Android Bloodborne port.
